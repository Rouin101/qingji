# 青迹开发约定

## 变更原则

- 每项改动先对应一个明确用户问题，再写验收条件和回归检查。
- 优先在现有证据链中增加字段或步骤，不生成无法回到材料的孤立输出。
- 模型负责建议，授权、引用资格、最终状态和成果选择保持独立检查。
- 真实验证先于复杂算法；没有冻结评测集时，不以更复杂模型替代问题定位。
- 不把真实材料、数据库、密钥、原文、脱敏文件或导出成果提交到 Git。

## 本地验证

提交前从仓库根目录运行：

```powershell
.\scripts\test.ps1
```

该脚本应完成自动化测试、语法检查、隔离数据库端到端流程、固定检索回归和虚构综合评测。涉及数据库或备份时，还应验证旧库升级和项目备份往返。

## 提交要求

1. 一个提交只处理一个可说明的目标，避免混入无关格式化。
2. 变更说明写清用户问题、边界变化、迁移影响和实际运行的检查。
3. 用户可见变化更新 `CHANGELOG.md`；数据字段变化更新数据字典和迁移说明。
4. 版本标签只在工作区干净、完整测试通过且文档同步后创建。

## 发布节奏

- `alpha`：能力和数据结构可继续变化，用于内部开发与小规模试用。
- `beta`：核心流程和迁移策略稳定，开始冻结真实评测口径。
- 稳定版：真实试用问题已经收口，升级、备份、恢复和边界文档可复查。

原则上每两周审阅一次近期问题清单；只有达到发布门禁时才建立版本标签。是否推送远端由项目负责人单独决定，本地提交和标签不自动发布。
